# ADR-001 — ORM : Drizzle (0.45.x stable)

**Statut** : accepté — 2026-09-17

## Contexte

Le schéma est lu et écrit par deux processus (app Next, worker) via `packages/core`. Deux besoins SQL dépassent le CRUD :

- la déduplication par similarité (`pg_trgm`, `similarity()`, index GIN) ;
- les `INSERT … ON CONFLICT` en masse pendant l'ingestion.

Le projet est local, avec un seul développeur, et doit rester minimaliste.

Versions vérifiées :

- `drizzle-orm` 0.45.2 / `drizzle-kit` 0.31.10 (stables) ;
- `drizzle-orm` 1.0.0-rc.4 (tag `rc`) ;
- `prisma` : le dist-tag `latest` du CLI pointe sur **8.0.0-rc.15**, alors que `@prisma/client` `latest` est en 7.10.0 et `prev` = 7.10.0. La dernière stable est donc la **7.10.0**.

## Options

1. **Prisma 7.10**. Le guide de migration v7 impose :
   - le générateur `prisma-client` avec `output` obligatoire (le client n'est plus généré dans `node_modules`) ;
   - des **driver adapters obligatoires** (`@prisma/adapter-pg`) ;
   - `prisma.config.ts` ;
   - l'ESM ;
   - le chargement explicite de `.env`.

   Cela fait une étape de génération à orchestrer pour deux consommateurs, et le SQL trigram passe par `$queryRaw` non typé. Enfin, un `latest` en RC sur le CLI est un signal de confusion à éviter pendant la majeure 8.
2. **Drizzle 0.45 (stable)**. Schéma en TypeScript pur, importable tel quel par Next (`transpilePackages`) et par le worker (`tsx`), sans génération. Le SQL explicite est typé (`sql\`similarity(...)\``) et `onConflictDoUpdate` est natif. Les migrations SQL sont lisibles.
3. **Drizzle 1.0 RC**. Évite une migration future, mais c'est une RC : la règle du projet est de n'utiliser que des versions stables.
4. **SQL brut (`postgres.js`)**. Le plus léger, mais le typage des lignes est à écrire à la main, sans outil de migration.

## Décision

**Drizzle ORM 0.45.2 + drizzle-kit 0.31.10**, avec le driver `postgres` (postgres.js 3.4.9).

Pour rendre la future migration vers 1.0 quasi gratuite, on s'appuie sur ce que le guide v0 → v1 annonce comme changements cassants :

- **pas d'API relationnelle v1** (`db.query.*` + `relations()`), qui est supprimée en 1.0 au profit de `defineRelations()`. On utilise le query builder `select/insert/update` et des jointures explicites ;
- **pas de `drizzle-zod`**, absorbé dans `drizzle-orm/zod` en 1.0. Les schémas zod du domaine sont écrits à la main dans `core/domain`, ce qui est de toute façon souhaitable : le contrat métier n'est pas la forme de la table ;
- **pas d'option `casing`** globale (elle change d'API en 1.0) : les noms de colonnes sont explicites (`text('title_norm')`) ;
- **pas de `.array().array()`** ni de RLS.

## Conséquences

- Une étape `drizzle-kit generate` → fichiers SQL versionnés dans `packages/core/drizzle/`, puis `drizzle-kit migrate` (exposé en `pnpm db:migrate`). En 1.0, le format des dossiers de migration change (plus de `journal.json`) : il faudra lancer `drizzle-kit up`.
- Les requêtes de dédup trigram s'écrivent avec `sql` et restent typées en sortie.
- Signal de révision : Drizzle 1.0 stable → migration (voir ROADMAP « Reporté »).
